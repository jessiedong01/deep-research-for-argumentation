\section{Method}
\label{sec:method}

\begin{figure}[t]
\centering

\caption{The three phases of \sys{}. In Phase 1, a literature search provides context for decomposing the question into a DAG of sub-questions. In Phase 2, leaves are answered by literature search, parents are composed from their children, and nodes whose answers are incomplete are refined with new sub-trees. In Phase 3, the answered DAG is turned into an outline and a report that argues for the root answer.}

\sys{} takes a research question and returns a report that argues for an answer to it, with inline citations to web sources. It runs in three phases, namely DAG generation, recursive processing, and report generation. This section describes the pipeline as it was when the reports in \Cref{sec:experiments} were generated, and \Cref{app:changes} describes the code versions involved. Every language-model call is implemented as a DSPy signature \citep{khattab2024dspy}, and the signatures are reproduced in \Cref{app:prompts}.

\paragraph{Literature search.}
The planning phase and the leaf nodes share one literature-search routine. A planning model turns a question into web queries. A retriever fetches the results through the Serper API, scrapes the pages, embeds their passages with \texttt{text-embedding-3-large}, and keeps the passages closest to the query. An answer model then writes a cited answer from these passages. After each round, a completeness check decides whether another search is needed, up to a fixed number of retriever calls per question.

\paragraph{Phase 1, DAG generation.}
A short literature search on the root question first gives the planner context about the topic. The planner then builds the DAG one layer at a time. For each node in the current layer it generates child sub-questions, conditioned on the node's question, the literature summary, the children generated so far, and the structure of the whole graph. Conditioning on the whole graph serves two purposes. It discourages siblings from overlapping, and it encourages the children of each node to cover its question jointly. The depth of the graph, the total number of nodes, and the number of children per node are capped. A second pass then writes composition instructions for every parent. Given the parent's question, its expected answer format, and the questions of its children, the model states how the children's answers should be combined into the parent's answer. These instructions refer to children by their identifiers, which makes each dependency explicit.

\paragraph{Phase 2, recursive processing.}
The DAG is sorted topologically and processed from the leaves to the root, since a parent can only be composed once its children have been answered. Leaves are answered in parallel by literature search, and the answer model writes bullet points in the node's expected format while keeping every citation from the search. Parents are then composed in sequence. The children's answers, the composition instructions, and the expected format are passed to a synthesis model, which may use only the content of the children, must cite using the children's citation numbers, and must state explicitly when the children contradict each other. Because a parent draws only on its children, every claim in its answer should trace back to evidence retrieved at a leaf.

A plan made before research can still omit something the research later shows to matter. After composing a parent, a gap explorer therefore lists possible omissions in the composed answer, and a gap evaluator decides, at a configurable level of conservatism, whether any omission is important enough to act on. If one is, the pipeline generates a sub-tree of new sub-questions that address the omission, attaches it beneath the parent, processes it in the same way as the rest of the graph, and composes the parent again. Each parent is refined at most once in the configuration used here.

\paragraph{Phase 3, report generation.}
The answered DAG is serialized as text, and its citations are collected into a single numbered list. An outline model, instructed to argue for a position on the root question, writes an outline whose sections follow the branches of the graph. A report model then writes the report from the outline and the graph. It keeps the citations, adopts the position of the root answer, and titles the report with the claim rather than the question. Finally, citation numbers are normalized and a bibliography is appended.

\begin{algorithm}[t]
\caption{\sys{}}
\label{alg:pipeline}
\begin{algorithmic}[1]
\Require motion $m$, limits on depth $d$, nodes $n$, and children $c$, refinement rounds $\rho$
\State $L \gets \textsc{LiteratureSearch}(m)$ \Comment{context for planning}
\State $G \gets$ root $r$ with $q_r = m$
\For{each layer $\ell = 0, \dots, d-1$} \Comment{Phase 1}
  \For{each node $u$ at depth $\ell$}
    \State add children $\textsc{PlanChildren}(q_u, L, G, c)$ under $u$, within the node limit $n$
  \EndFor
\EndFor
\For{each parent $u$} $\kappa_u \gets \textsc{CompositionInstructions}(q_u, \{q_v : v \in C(u)\})$ \EndFor
\For{each node $u$ in topological order, leaves first} \Comment{Phase 2}
  \If{$u$ is a leaf}
    \State $(a_u, S_u) \gets \textsc{AnswerFromSearch}(q_u)$
  \Else
    \For{$k = 0, \dots, \rho$}
      \State $a_u \gets \textsc{Compose}(q_u, \{a_v\}_{v \in C(u)}, \kappa_u)$, \quad $S_u \gets \bigcup_{v \in C(u)} S_v$
      \State $\Delta \gets \textsc{FindGaps}(q_u, a_u)$
      \If{$k = \rho$ \textbf{or} $\Delta = \emptyset$} \textbf{break} \EndIf
      \State attach a sub-tree for $\Delta$ under $u$ and process it as in Phase 2
    \EndFor
  \EndIf
\EndFor
\State $O \gets \textsc{Outline}(m, a_r, G)$, \quad $R \gets \textsc{Report}(O, m, a_r, G)$ \Comment{Phase 3}
\State \Return $R$ with a bibliography of $\bigcup_v S_v$
\end{algorithmic}
\end{algorithm}

\paragraph{Cost.}
Let $|V_\text{leaf}|$ and $|V_\text{par}|$ denote the numbers of leaves and parents after refinement. Each leaf requires one literature search, which comprises at least a query-generation call, a retrieval step with embedding, an answer call, and a completeness check. Each parent requires one composition call per round and one gap check. Planning adds one call per parent for its children and one for its instructions, and writing adds two calls. The number of model calls is therefore approximately $4|V_\text{leaf}| + (3 + 2\rho)|V_\text{par}| + 3$. This number grows linearly with the size of the graph, and the leaves can be processed in parallel. The logged run in \Cref{app:dag} has \dagLeaves{} leaves and \dagParents{} parents and so makes on the order of 40 model calls, compared with one or a few calls for a report written in a single pass.

\paragraph{Models and limits.}
The evaluation runs used GPT-4.1-mini for answer generation during retrieval and for planning, GPT-5 for DAG generation, synthesis, and report writing, and \texttt{text-embedding-3-large} for retrieval, all accessed through Azure OpenAI. The default limits cap the graph at depth 2, 50 nodes, and 10 children per node, with one retriever call per literature search and one refinement per parent.
